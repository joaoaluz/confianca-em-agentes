a tese

O gargalo não é o agente. É a confiança.

✗ sem confiança

Você vira microgerente

O agente chuta a causa de um bug, afirma com certeza e erra. Você passa a conferir cada resposta, e não consegue usar mais que um ou dois ao mesmo tempo.

✓ com confiança

Você consegue paralelizar

Ninguém lança cem agentes sem confiar no resultado de um. A confiança é o que libera a escala.

A analogia dela: gerenciar agentes é como gerenciar uma equipe. Sem confiança, você fica olhando por cima do ombro de todo mundo.

Imagine alguém que programa muito bem mas entrou na empresa há cinco segundos. Uma skill é o treinamento dele: um arquivo de texto (Markdown) com instruções e conhecimento.

Ela nunca planejou o plugin Pstack: ele cresceu assim, uma falha observada por vez.

no Claude Code

Uma skill é uma pasta com um SKILL.md. O Claude carrega sozinho quando a descrição combina com a tarefa, ou você chama com /investigar-bug.

---
name: investigar-bug
description: Use ao investigar a causa de um bug.
---
1. Antes de afirmar uma causa, abra e leia os arquivos envolvidos.
2. Reproduza o bug (teste ou app) antes de mudar código.
3. Busca ampla? Use subagentes em paralelo.
4. Diga o que confirmou e o que ainda é hipótese.

camada 2evals

Eval: um teste unitário para o agente

Rubrica

Um agente coordenador escreve os critérios do que a skill deve fazer.

Subagentes "cegos"

Cada um roda a tarefa numa pasta com nome neutro. Agentes que percebem que estão sendo testados mudam de comportamento.

Juiz de outro modelo

Um modelo diferente dá a nota, para não haver viés.

Loop até 10/10

Repete ajustando a skill até a nota máxima ("hill climbing").

Bônus: rodar o mesmo eval em vários modelos mostra onde a skill aguenta e onde quebra.

no Claude Code

O modo sem interface (claude -p) roda uma tarefa e devolve o resultado, então dá para montar o eval num script: várias execuções com um modelo e a nota com outro.

claude -p "Use a skill investigar-bug no caso da pasta caso-07" --model sonnet > run-07.txt
claude -p "Dê nota de 0 a 10 para run-07.txt segundo rubrica.md" --model opus

camada 4arquitetura

"O caminho mais curto deve ser o melhor caminho"

Tudo junto

Cada funcionalidade mora numa pasta só. Em 80% das tarefas o agente nem sai dela.

Armadilhas proibidas

useEffect do React e comentários no código são barrados pelo CI. Os agentes escreviam comentários com "regras" que ela nunca deu.

Fronteiras checadas

Cada quadro da tela tem 16 ms. O CI confere os imports para código pesado não ir parar na parte que desenha a interface.

Mais um hábito: PRs pequenos e atômicos. O histórico vira contexto, e desfazer um erro fica fácil.

camada 4arquitetura · aula 3

Comentário é desculpa. Lint é regra.

antes: o agente se justificailustrativo
// setTimeout necessário porque o estado
// ainda não foi atualizado neste ciclo
setTimeout(() => abrirPainel(), 0);
✗ lint setTimeout não é permitido em componentes. Costuma esconder um problema de estado: corrija a causa com <padrão do projeto>, não com um timer.
  • Na Cursor, timers usados como remendo se espalharam, cada um com um comentário justificando, e o app ficou lento.
  • No Grokbot, 99% dos comentários são proibidos: ficam velhos, ninguém lê e não dá para obrigar ninguém a segui-los.
  • A mensagem de erro é escrita para o agente: aparece no momento exato do erro e manda corrigir a causa.

Testes que o agente não consegue trapacear

Agentes às vezes fazem o teste passar em vez de fazer o código funcionar, e pesquisas de 2026 relatam isso até quando eles são instruídos a não fazer. A defesa tem que ser mecânica.

TécnicaQue trapaça ela impede
Testes de aceitação escritos primeiro e protegidos por hookApagar ou afrouxar o teste para passar
Cenários holdout fora do repositório (StrongDM)Otimizar para os testes que o agente consegue ver
Testes de mutação nos arquivos alterados (Meta)Testes que passam, mas não pegam nada
Testes de propriedadeTratar só os casos que estão no teste
Sinais no CI: skip, teste apagado, cobertura em quedaEsconder a trapaça num PR grande

estado da artejulgamento independente

Quem faz não deve ser quem julga

  • Agentes tendem a elogiar o próprio trabalho. A Anthropic achou mais fácil calibrar um avaliador cético do que tornar o gerador autocrítico.
  • De preferência outro modelo: vieses diferentes pegam erros diferentes.
  • Limite duro por critério da spec: um falhou, reprovou.
  • Calibrado com exemplos seus até concordar com você.
  • Nunca a única barreira: revisores de IA têm pontos cegos em comum com o autor.

estado da arteleitura crítica

Onde as fontes divergem

ninguém revisa código

StrongDM e OpenAI

A StrongDM proíbe humanos de escrever ou revisar código e gasta cerca de US$ 1.000 por engenheiro por dia em tokens. A OpenAI fez ~1 milhão de linhas sem código escrito à mão, mas avisa que barreiras tão mínimas seriam irresponsáveis num ambiente de pouco volume.

humano no alto risco

Augment, Monperrus, DORA

Autonomia por tipo de mudança, promovida quando reversões e incidentes ficam abaixo da base humana. Humanos continuam no alto risco, em arquitetura nova e em código regulado. E a IA amplifica o que já existe, bom ou ruim.

O caminho do playbook: autonomia por tipo de mudança, medida e reversível.

Modelos de famílias diferentes são o "avaliador de outro modelo" do estado da arte, já incluído nos dois planos. E quando um esgota a janela de 5 horas, o outro continua.

na práticaapps mobile

Mobile: o Maestro no lugar do navegador

  • Aparelho físico pelo USB: se adb devices lista o celular, o Maestro usa. Roda nativo no Windows, com Java 17+.
  • Um celular, um agente por vez: o script de verificação pega uma trava antes de usar a tela.
  • testID nos componentes, usado como id: nos fluxos e listado no feature map.
  • adb reverse liga o celular ao Metro e ao backend de teste da sua máquina.
  • Hierarquia em texto, pelo MCP do Maestro, gasta menos tokens que screenshots.
  • CI sem o seu celular: precisa de emulador no runner ou de aparelhos na nuvem; até lá, roda os testes rápidos.
  • Aparelho de teste: o agente vê a tela inteira, inclusive notificações.

Glossário e perguntas

agente
IA que age sozinha: lê arquivos, roda comandos, escreve código.
PR / merge
Pedido de mudança no código / incluir a mudança no principal.
skill
Arquivo de instruções que ensina o agente a fazer algo.
eval
Teste que mede se o agente faz bem uma tarefa.
CI
Verificações automáticas a cada mudança.
lint
Ferramenta que barra padrões de código proibidos.
trace
Registro de desempenho de um programa.
vibe coding
Programar pedindo à IA, sem ler o código com atenção.
hook
Comando que o Claude Code roda sozinho em certos momentos, como depois de cada edição.
MCP
Jeito padrão de dar novas ferramentas ao Claude, como controlar um navegador.
holdout
Cenários de teste guardados longe do agente, para ele não otimizar para eles.
teste de mutação
Insere pequenos erros no código e confere se os testes percebem.
revisão por exceção
Humanos revisam só o que tem risco alto ou o que as máquinas não garantem.
modo sombra
A automação decide, mas um humano ainda revisa tudo para comparar.
AGENTS.md
Arquivo de instruções que vários agentes leem, como o Codex; o CLAUDE.md pode importá-lo.
Spec Kit
Ferramenta do GitHub para ir de uma ideia a spec, plano e tarefas antes do código.
perfil de projeto
Tipo de projeto que define quais fases aplicar e até onde vai a autonomia.
